## Как этот план соотносится с дорожной картой

План **не переопределяет** утверждённую владельцем последовательность
(OWNER-ROADMAP-DECISION-003: UX-first → operator walkthrough → недостающие бизнес-функции →
KSO/player + signed licensing → pilot → production hardening) и не вводит новых волн.

Он вставляет **один короткий блок W0+ перед Wave 1** и распределяет остальное по уже
существующим волнам. Обоснование блока W0+: это дефекты правды и канона. Пока они открыты,
любая последующая работа опирается на источник, который может ввести в заблуждение, —
а стоимость их устранения измеряется часами.

| Волна дорожной карты | Что добавляет этот план |

## Блок W0+ · Правда и канон (перед Wave 1)

### WP-1 · Снять противоречие в порядке разрешения конфликтов 🔴 P0 · ~2 ч

**Проблема:** A1 — `CLAUDE.md` ставит код выше архитектурных документов, а
`docs/00-source-of-truth/README.md` объявляет, что папка канона выигрывает у кода. Правила
взаимоисключающие, при этом `CLAUDE.md` сам предписывает при противоречии остановиться.

**Работы:**
1. Владелец выбирает одно правило (рекомендация ниже).
2. Правило записывается **в одном месте**, второй документ ссылается на него, а не повторяет.
3. Явно описать случай «код разошёлся с ТЗ»: что считается истиной и какой артефакт обязателен
   для легализации расхождения (ADR).

**Рекомендация аудитора.** Оставить приоритет `CLAUDE.md` (код — истина о том, *что система
делает*), но добавить оговорку: **расхождение кода с папкой источника истины не является
разрешённым само по себе** — оно требует ADR, иначе считается дефектом. Это сохраняет
работоспособность («код не врёт») и закрывает лазейку, через которую прошёл B1.

**Приёмка:** в репозитории ровно одно определение порядка истины; выбранное правило разрешает
кейс B1 однозначно; ссылка на него есть в `AGENTS.md`, `CLAUDE.md` и обоих README.

**Зависимости:** решение владельца. **Блокирует:** WP-2.

### WP-2 · Решение по подписи манифеста: Ed25519 или осознанный HMAC 🔴 P0 · ~1 ч решение + 8–16 ч реализация

**Проблема:** B1 — канон требует «Ed25519 для production, HMAC только для dev/mock», код
реализует только HMAC-SHA256, ADR-013/016 говорят «Ed25519 или HMAC» без производственного
ограничения, а производственный гейт закрепляет сильный HMAC-ключ как норму.

**Работы — развилка, решает владелец:**

*Вариант A — привести код к канону (рекомендуется до масштабирования парка):*
1. Реализовать подпись Ed25519 в `packages/contracts/manifest_signing.py`
   (значение `ED25519` в перечислении уже есть).
2. Устройство получает **только публичный ключ**; приватный не покидает control-plane.
3. Производственный гейт: в `production`/`staging` требовать Ed25519, HMAC разрешить только
   в `dev`.
4. План ротации и совместимости: поле `manifest.signature.algorithm` уже предусмотрено
   контрактом, значит возможен период двойной поддержки.

*Вариант B — легализовать HMAC на этапе пилота:*
1. ADR (или дополнение к ADR-016) с явной формулировкой: «для control-plane pilot допускается
   HMAC-SHA256; Ed25519 обязателен до масштабирования свыше N устройств».
2. Записать риск в дорожную карту с триггером перехода.
3. Оставить производственный гейт как есть, но с явной ссылкой на это решение.

**Почему это P0 при любом варианте:** сейчас расхождение не зафиксировано нигде, и гейт
готовности к проду проверяет *не тот* алгоритм. Даже если выбран вариант B, стоимость — один
документ.

**Приёмка:** выбранный вариант оформлен ADR; производственный гейт и код соответствуют ADR;
tamper-тест (подмена алгоритма → красный) при варианте A.

**Зависимости:** WP-1 (правило разрешения расхождений).

### WP-3 · Единый контракт `BEHAVIORAL_APP_DB_URL` 🟡 P1 · ~2 ч

**Проблема:** находка утреннего аудита — переменная перегружена двумя несовместимыми
форматами, общего значения не существует. Форма SQLAlchemy ломает два новейших доказательства
безопасности (`ClientConfigurationError`), сырой DSN ломает всю остальную behavioral-сессию
(`InvalidRequestError: … 'psycopg2' is not async`). CI молчит, потому что переменную не
выставляет.

**Работы:**
1. Один хелпер, приводящий URL к нужной форме для каждого потребителя (`to_sqlalchemy_url` /
   `to_raw_dsn`).
2. Все точки чтения переменной — через хелпер.
3. Тест: при обеих формах значения набор полностью зелёный.
4. Раздел «Environment» в `PROJECT_STATE.md` — привести к реальности.

**Приёмка:** прогон с `postgresql://…` и с `postgresql+asyncpg://…` даёт одинаково зелёный
результат; тест на обе формы в CI.

### WP-4 · Сделать честный RLS-контекст умолчанием behavioral-набора 🟡 P1 · ~4–6 ч

**Проблема:** находка утреннего аудита — общий conftest открывает каждую сессию с
`app.rmp_is_admin='true'`; сброс живёт в `resolve_scope_context`, вызываемой только через
`set_rls_context`. Эндпоинт, забывший контекст, в тестах видит **все** строки, в проде —
**ноль**. Набор структурно слеп к классу дефектов, который уже дважды реализовался
(`INVENTORY-RLS-CONTEXT-001`, молчаливый `null` в `/auth/me`).

**Работы:**
1. Строгий `get_db` (без предэлевации) — **умолчание** набора.
2. Admin поднимается точечно, только в фикстурах подготовки данных.
3. Проверка покрытия: тест, требующий `Depends(set_rls_context)` у каждого эндпоинта,
   читающего таблицу под FORCE RLS (сейчас 111 из 114; три исключения — глобальные таблицы —
   вносятся в явный allowlist с обоснованием).
4. Tamper: снять контекст с одного эндпоинта → набор краснеет.

**Приёмка:** tamper даёт красный; полный behavioral-набор зелёный под строгим умолчанием;
`strict_client` как отдельная фикстура больше не нужен.

**Ценность:** это единственная работа в плане, которая **предотвращает** повторение P0, а не
чинит последствия.

## Wave 1 · Дополнения

### WP-5 · Зафиксировать SLO из ТЗ §22.2 и начать их измерять 🟡 P1 · ~6–10 ч

**Проблема:** C5 — ни одна из целевых цифр (портал ≥99,5%, gateway ≥99,9%, манифест ≤5 мин,
emergency ≤1 мин, потери PoP ≤0,1%) не зафиксирована как SLO и не измеряется.

**Работы:**
1. ADR или раздел в ADR-005: перечень SLO, окно измерения, владелец, что считается нарушением.
2. Метрики и панели под каждый SLO; там, где измерение пока невозможно (нет реального КСО) —
   явно пометить «не измеряется, причина».
3. Порог потерь PoP — отдельно: требует счётчика ожидаемого объёма, иначе цифра недоказуема.

**Приёмка:** каждый SLO имеет либо метрику, либо явную отметку о невозможности измерения с
причиной. Эксплуатация пилота без этого — «на глаз».

**Зависимость:** осмысленно делать до Wave 4 (pilot), иначе пилот нечем оценивать.

## Wave 2 · Разрывы ТЗ в бизнес-логике

### WP-7 · Классификация причин недопоказа (ТЗ §22.3) 🟡 P2 · ~12–20 ч

Есть: детект недопоказа (план/факт/отклонение) и маркировка `placement_basis='compensation'`.
Нет: таксономии причин.

1. Перечисление из 8 категорий ТЗ + типовые причины (офлайн устройства, закрыт магазин, медиа не
   скачалось, SHA-256 не совпал, манифест не применён, истёк `valid_to`, вытеснение emergency,
   вытеснение приоритетом).
2. Проставление причины по данным доставки и PoP — там, где выводимо автоматически.
3. Блок в отчёте: план, факт, % выполнения, недопоказ, причины, компенсация.

**Зависимость:** часть причин выводима только при живом потоке PoP → полная ценность после Wave 3.
**Рекомендация:** сделать модель и ручное проставление в Wave 2, автоматический вывод — в Wave 3.

### WP-8 · Вытеснение и приоритеты (ТЗ §22.4) 🟡 P2 · ~20–30 ч

Сейчас: поле `priority` есть, логики вытеснения нет (0 реализации).

1. Формализовать иерархию приоритетов из ТЗ (emergency → обязательная сеть → федеральные →
   филиальные → локальные → filler → тестовые), версионируемую через админ-интерфейс.
2. Показывать, **какая кампания вытесняет какую и почему** — прямое требование ТЗ.
3. Запрет публикации при критичных конфликтах без подтверждения уполномоченного.
4. Правила применяются с даты изменения и **не меняют исторические отчёты** ретроспективно.

### WP-9 · Overbooking как настраиваемая политика (ТЗ §22.4) 🟢 P2 · ~4–6 ч

Детект `CAPACITY_OVERBOOKED` в симуляции уже есть. Не хватает настройки уровня платформы
«overbooking запрещён/разрешён», **по умолчанию запрещён**, и связи детекта с политикой.

## Wave 3 · Деньги и качество контента

### WP-10 · Развести биллинговый пик и ёмкость до Layer 2 🟡 P2 · ~6–10 ч

Находка утреннего аудита: ёмкость считается по всей инсталляции, а оплачиваемый пик seat-month —
по конкретному гранту. Сегодня латентно (продление не реализовано, singleton-индекс не даёт
второго `current`). При продлении места останутся на вытесненном гранте: сверка сообщит
`seat_under_noncurrent_grant` со степенью `error` и **не починит** — оплачиваемый пик тихо
станет нулём при занятости N.

1. Выбрать границу: пик по инсталляции **или** перевешивание мест при продлении.
2. Реализовать восстановление для `seat_under_noncurrent_grant`, а не только детект.
3. Behavioral-тест на сценарий продления с непустым парком.

**Делать до реализации подписанной лицензии (Layer 2), а не после первого счёта.**

### WP-11 · Автоматический Creative QA (ТЗ §22.5) 🟡 P2 · ~16–24 ч

Есть: MIME, размер, SHA-256. Нет: антивирус (0), кодек/FPS/битрейт (0), песочница HTML5.

1. Технические проверки медиа (кодек, FPS, битрейт, длительность, разрешение, отсутствие звука).
2. Антивирусная проверка загружаемых файлов, запрет исполняемых.
3. Решение ИБ по HTML5: запретить на первом релизе либо ограниченная песочница (ТЗ допускает оба).
4. Хранение результата проверки: кто, когда, что пройдено, какая версия допущена.

**Приоритет внутри блока:** антивирус и запрет исполняемых — вперёд, это безопасность, а не качество.

## Wave 4/5 · Масштаб

### WP-12 · План перехода на ClickHouse с проверяемым триггером 🟡 P2 · ~4 ч (планирование)

ADR-007 откладывает ClickHouse до «>10 млн событий/день» — решение корректное. Но при целевом
парке 40 000+ устройств порог перекрывается примерно в шесть раз (≈57,6 млн событий/сутки при
одном показе в минуту), а переход не запланирован ни в одной волне.

1. Записать расчёт в ADR-007 или дополнение — чтобы порог был сопоставим с целевым парком.
2. Ввести **измеряемый** триггер: метрика фактического объёма PoP + порог оповещения заранее.
3. Внести переход в дорожную карту как элемент Wave 5, с зависимостью от реального объёма.

Реализацию **не** начинать: для пилота PostgreSQL достаточно, ранняя миграция — трата.

## Что этот план сознательно НЕ трогает

- **Дорожную карту `docs/product/roadmap.md`** — не изменялась, остаётся каноном
  последовательности.
- **Утверждённые решения владельца** (OWNER-ROADMAP-DECISION-003): UX-first, control-plane pilot
  scope, реальный КСО вне ближайшего пилота, отсутствие календарной даты для production.
- **Operator walkthrough** — закрывает только человек, агент этого не делает.
- **Реестр функций** — статусы меняются только вместе с доказательством.
- **Незакрытые исходные решения** (MFA, согласование NATS с ИТ, параметры реального КСО) —
  это вопросы к владельцу и внешним сторонам, а не работы агента.
