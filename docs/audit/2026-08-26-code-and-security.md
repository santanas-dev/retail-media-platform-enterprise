## 2. Проверено своими руками

### 2.1 AUTHZ-CROSS-PORTAL-001 (P0) — ЗАКРЫТО, миграция 035

Реальный дефект, а не ложная тревога. Миграция 020 отнесла дочерние таблицы кампании к
«производным» и выдала политику только по ритейлеру, потеряв измерение рекламодателя,
которое задавали миграции 006/010. Следствие: два рекламодателя **одного** ритейлера
видели чужие рейсы, размещения, креативы, согласования и историю статусов через обычные
list-эндпоинты. Таблица `campaigns` не затронута — у неё есть `advertiser_organization_id`,
поэтому в списке кампаний дефект не проявлялся.

Миграция `035_derived_tables_advertiser_rls.py` переводит SELECT/INSERT/UPDATE/DELETE пяти
дочерних таблиц на `admin OR (retailer_id ∈ retailer_scope AND campaign_id ∈ видимые
кампании advertiser_scope)`.

**Мой прогон.** Фикстура: 1 ритейлер, 2 организации рекламодателей (ORG_A, ORG_B), у каждой
полное поддерево кампании. Запрос под `scope = ORG_A`:

| Таблица | Свои (035) | Чужие (035) | Чужие после `downgrade 034` |
|---|---:|---:|---:|
| `campaign_flights` | 1 | 0 | **1** |
| `campaign_placements` | 1 | 0 | **1** |
| `campaign_approvals` | 1 | 0 | **1** |
| `campaign_status_history` | 1 | 0 | **1** |
| `campaigns` | 1 | 0 | 0 |

Дополнительно:

- пустой advertiser-scope → **0** строк (fail-closed);
- админ → **2** строки (доступ не сломан);
- вставка в чужую кампанию → `ERROR: new row violates row-level security policy for table "campaign_flights"`.

**Tamper-цикл выполнен:** `alembic downgrade 034` → утечка вернулась на всех четырёх
таблицах; `alembic upgrade head` → снова закрыта. Это подтверждает, что закрывает утечку
именно 035, а не побочный эффект.

**Границы исправления проверены отдельно.** Таблицы `delivery_*`, `pop_*`,
`inventory_bookings` и инвентарь ритейлера сознательно не тронуты; обоснование в миграции
согласуется с кодом (device-gateway ставит только retailer-scope; `inventory_bookings`
за `inventory.read`, которого у роли `advertiser` нет).

к request-scope. Пол версии поднят до `fastapi>=0.121.0` с эмпирической проверкой
(0.120.0 — нет, 0.121.0 — есть).

(велик соблазн «починить» их удалением).

### 3.2 BEHAVIORAL-ADMIN-MASK-001 — 🟡 тест-фиделити

`tests/behavioral/conftest.py::_override_get_db` открывает **каждую** сессию запроса с
`set_config('app.rmp_is_admin','true')`. Сброс флага в `false` живёт в блоке `finally`
функции `resolve_scope_context`, а она вызывается только через `get_scope_context` —
зависимость `set_rls_context`.

Следствие (проверено по коду): эндпоинт, который RLS-контекст **забыл**, флаг не
сбрасывает — в тестах он видит **все** строки, а в проде fail-closed отдаёт **ноль**.
Оба поведения неверны, и набор скрывает разницу.

Это ровно тот класс, что дал `INVENTORY-RLS-CONTEXT-001` и молчаливый `null` в
`/auth/me`. Команда о нём знает и завела фикстуру `strict_client`, но **только в одном
файле**. Пока честная зависимость не станет умолчанием для всего набора, следующий
забытый контекст снова доедет до стенда с зелёным CI.
Тот же класс, что закрытая ранее `SMOKE-FIDELITY-001`.

**Лечится:** сделать строгий `get_db` умолчанием набора, поднимать admin только в
фикстурах подготовки данных.

### 3.3 LICENSE-PEAK-GRANT-SCOPE-001 — 🟡 Контур 1, денежная граница, латентно

Разные границы учёта в одном отчёте:

- `count_occupied_seats` — считает занятость **по всей инсталляции** (все открытые места);
- `peak_seats_for_month(license_id=grant.id)` — считает пик за месяц (тот самый seat-month,
  по которому выставляется счёт) **по конкретному гранту**.

**Сегодня не стреляет, и это я проверил, прежде чем считать находкой:** продление не
реализовано — уникальный индекс `uq_license_grants_single_current` не даёт появиться
второму гранту в статусе `current`, а статус `superseded` не выставляется нигде в
продуктовом коде (только в тестах и в CHECK-ограничении). `license-dev-ingest.py`
вставляет один грант с `ON CONFLICT DO NOTHING`.

**Что произойдёт при продлении.** Существующие места останутся привязанными к вытесненному
гранту. Сверка честно сообщит `seat_under_noncurrent_grant` со степенью `error`
(`licensing_service.py:549`) — **и не починит**: `reconcile_existing_fleet` создаёт места
только устройствам, у которых открытого места нет вовсе, а такие устройства его имеют.
Итог: занятость показывает N, а оплачиваемый пик тихо читается как ~0.

**Рекомендация:** решить до EPIC-L Layer 2 (подписанная лицензия/продление) — либо считать
пик по инсталляции, либо перевешивать места на новый грант в момент продления. После
первого счёта это будет спор с клиентом, а не рефакторинг.

Сам choke-point зачисления мест проверен и сделан аккуратно: одна транзакция,
`SELECT … FOR UPDATE` на единственном текущем гранте, подсчёт занятости после блокировки,
проверка ёмкости, минт устройства и резерв места; частичные уникальные индексы
(`uq_license_grants_single_current`, `uq_license_seats_open_per_device`) на месте.
Прогнал их behavioral-набор на своей БД: `test_license_seat_ledger` + `test_license_enrollment`
— **33 passed**; `test_license_decommission` + `test_license_report` + authz/split — **66 passed**
(2 падения — это находка 3.1, дефект контракта env, а не продукта).
