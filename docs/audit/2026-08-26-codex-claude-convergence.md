## 1. Общая позиция после взаимного ревью

Codex и Claude согласны по C2–C8 и по необходимости остановить расширение UX до
восстановления достоверности gates. Разногласия сведены к точным формулировкам:

1. **C1 остаётся дефектом Done Gate.** Прямой API, повторный deep `page.goto`, `sleep` и
   недетерминированные retry не соответствуют обязательному пути реальными кликами. Пока smoke
   не исправлен и не перепрогнан, он не является достаточным доказательством `reachable`.
2. `except Exception` в `advertiser.invite` ухудшает диагностику и скрывает нестабильность, но
   сам по себе не создаёт ложный green: после цикла есть финальная проверка. Это 🟡, не 🔴.
3. **C3 подтверждён в узкой формулировке:** unscoped `operator` и `analyst` проходят часть
   permission-gates, но получают пустой tenant-scope и не видят tenant-данные. Существующий
   `test_adr018_multitenancy_rls.py` уже доказывает no-scope operator на campaign briefs;
   эксперимент Claude расширяет наблюдение на analyst и пять таблиц.
4. Нельзя без отдельного автоматизированного прогона обобщать результат на «все 36 таблиц» или
   утверждать отсутствие влияния на живых пользователей только по содержимому seed.
5. Текущий `resolve_scope_context` буквально следует ADR-018, шагу 9: retailer scope выводится
   из advertiser organization. Доступ внутренних persona в ADR не определён; это пробел решения,
   а не прямое нарушение существующего текста ADR.
6. WP-4 и CA-1 независимы. Для единой последовательности рекомендуется сначала WP-4 как защита
   tenant isolation, затем CA-1 как восстановление достоверности UI-доказательств.

## 2. Единый рабочий контракт

До переноса решений в канон оба агента используют следующий процесс как предложение, не как
самовольное изменение правил:

- владелец утверждает архитектуру, protected boundaries и изменение канона;
- Codex проектирует, проверяет доказательства и принимает/отклоняет результат;
- Claude Code — единственный implementation agent;
- аудит фиксирует наблюдение, `PROJECT_STATE.md` хранит исполняемый статус, ADR хранит принятое
  архитектурное решение, `feature-registry.yaml` хранит статус journey;
- каждое утверждение о готовности содержит SHA, точную команду и результат; статический анализ
  не заменяет behavioral proof;
- опубликованные аудиты не переписываются: исправление оформляется новой записью;
- при конфликте кода с ADR/TЗ фиксируется различие «текущее поведение» против «целевого
  контракта», работа останавливается до решения владельца.

## 3. Рекомендуемые решения владельца

### D1. Actors, RBAC и tenant scope

**Рекомендация:** actor в journey — продуктовая persona, а не неявный синоним роли. Для каждой
persona указываются backend role code и обязательные permission codes. Внутренние роли делаются
least-privilege bundles и получают первоклассный `scope_type='retailer'`; advertiser остаётся
advertiser-scoped. `system_admin` и `security_admin` остаются единственными admin-bypass ролями.

После одобрения решение оформляется дополнением/новым ADR к ADR-018. Простое добавление
`operator`/`analyst` в `ADMIN_ROLE_CODES` отклоняется: оно разрушает tenant isolation.

### D2. Роль UI-smoke в CI

**Рекомендация:** UI-smoke не входит в обычный pytest/unit gate, но является обязательным
отдельным gate для `develop`, release/pilot claim и статуса `reachable`. Это сохраняет быстрый
обычный CI и соответствует фактически реализованному `release-gate`. Пункт 6 Done Gate должен
быть переписан однозначно после одобрения владельца.

### D3. Подпись manifest

**Рекомендация:** сохранить Ed25519 как целевой канон; production-config gate не должен выдавать
готовность по HMAC. Решение и корректировка gate нужны сейчас, реализация/совместимость устройства
— обязательны до Wave 3 и первого device pilot. Изменение device contract выполняется только
после отдельного явного одобрения protected boundary.

### D4. Единственная очерёдность

**Рекомендация:** `pre-pilot-journey-plan.md` — единственный канонический порядок волн.
Действующее содержимое `roadmap.md` переносится туда либо `roadmap.md` включается в индекс с
однозначно более низким приоритетом. XLSX остаётся производной бизнес-картой и не задаёт порядок.

## 4. Единая последовательность реализации

После одобрения D1–D4 и фиксации workstream в `PROJECT_STATE.md`:

1. **WP-4 → WP-3:** строгий RLS-контекст behavioral-набора и единый DB URL.
2. **CA-1:** удалить API/deep-navigation/timing/retry нарушения из UI-smoke, добавить AST guard,
   перепрогнать затронутые journey.
3. **CA-2:** зафиксировать persona → role → permissions → retailer/advertiser scope; закрыть
   нормативные journey и positive/negative UI-smoke не под break-glass.
4. **CA-3 → CA-6:** синхронизировать CI-контракт, метрики, mutator scripts и freshness канона.
5. Возобновить `PORTAL-UX-POLISH-001A3` только после зелёных targeted gates и обновления
   `PROJECT_STATE.md`; operator walkthrough остаётся `PENDING` до человеческого прогона.

Работы выполняются последовательно: в репозитории один implementation agent. «Параллельно»
означает только отсутствие логической зависимости, а не одновременные несогласованные изменения.

## 5. Минимальный Done для блока стабилизации

- ни один UI-smoke после entry page не использует прямой API, deep `page.goto`, `sleep` или
  broad retry; guard ловит повторное появление;
- есть behavioral и UI positive/negative proof для хотя бы одной не-admin внутренней persona с
  retailer scope;
- normative journey, registry и smoke используют один journey id и согласованные actor/permission;
- CI semantics в `AGENTS.md` совпадает с workflow;
- команды, SHA и результаты записаны в `PROJECT_STATE.md`; операторская галочка не выставляется
  агентом.
