## 3. Возражения и уточнения

### 3.1 C1 · согласен с дефектом, возражаю против радиуса поражения

Нарушения реальны и подтверждены. Но «затронутые `reachable`-claims требуют исправленного smoke
и повторного прогона» — сильнее, чем следует из фактов, потому что смешивает **подготовку
данных** и **проверяемое утверждение**.

В `audit__view` API-вызовы `emergency/activate|deactivate` создают событие, которое затем
проверяется **в UI**. Проверяемая функция — `audit.view`, «оператор видит журнал аудита», и она
доказывается кликами. Сами `emergency.activate` / `emergency.deactivate` имеют **отдельные
собственные смоуки**, которые идут через интерфейс. То есть нарушено правило о способе
подготовки, но конкретный `reachable`-claim для `audit.view` не рассыпается.

Предлагаю разделить C1 по степени риска — они разной природы:

| Что | Риск | Оценка |
|---|---|---|
| broad `except Exception` + retry-цикл (`invite`) | **может скрыть настоящий сбой** — это риск правды | 🔴 |
| прямой API вместо кликов для подготовки | подмена способа доказательства; claim устоял, правило нарушено | 🟡 |
| `time.sleep(0.3)` | риск нестабильности, тот самый класс UI-SMOKE-FLAKE-001/002/003 | 🟡 |

Согласен, что **AST-guard из CA-1 п.5 нужен именно потому**, что нынешний guard проверяет имя
функции, а не семантику: без него любой будущий смоук уедет туда же незаметно.

### 3.2 CA-2 · оценка 8–16 ч оптимистична

13 полноценных journey-спецификаций (actor, permission codes, entry page, happy-path по шагам,
селекторы, negative-ожидание) плюс расширение guard плюс positive/negative прогоны не под
break-glass — это скорее **16–30 ч**, и это без учёта времени владельца на решение по actors.
Само решение поддерживаю: без него пункт 5 CA-2 неисполним.

### 3.3 Последовательность · WP-4 не должен ждать CA-1

Codex ставит `CA-1` → `WP-3/WP-4`. Обе работы дешёвые, но они защищают разное:

- **CA-1** восстанавливает доверие к **UI-доказательствам**;
- **WP-4** (строгий RLS-контекст умолчанием) закрывает то, что набор **структурно слеп к
  забытому RLS-контексту** — классу, который уже дважды реализовался: `INVENTORY-RLS-CONTEXT-001`
  и молчаливый `null` в `/auth/me`, причём второй всплыл при расследовании P0-утечки.

Пока WP-4 не сделан, следующая дыра в изоляции арендаторов снова доедет до стенда зелёной.
Предлагаю **WP-4 параллельно с CA-1 или первым**; они не конфликтуют по файлам.

### 3.4 B1 · сходимся, с одной оговоркой

Переквалификацию принимаю: устройств, проверяющих манифесты, сегодня нет, pilot не развёрнут,
production NO-GO — значит **реализация** Ed25519 обязательна до Wave 3 / первого устройства, а не
сейчас. Оговорка одна: **production-config gate уже сегодня валидирует не тот алгоритм** и

не дни. Формулировка Codex «decision сейчас» это покрывает — фиксирую, что расхождения нет.

## 4. Новые данные к находке C3 — усиливаю

C3 (product roles ≠ исполняемая RBAC-модель) сформулирована как расхождение документации. По
моему чтению кода она, вероятно, **ещё и функциональная**, и у неё есть конкретный механизм:

- `packages/domain/scopes.py` обрабатывает **только** `scope_type == "advertiser"` (строка 132);
  ветки для `retailer` нет;
- `retailer_scope_ids` заполняется **исключительно** производным путём — из advertiser-организаций
  (`if advertiser_scope_ids: retailer_scope_ids = await _load_retailer_ids(...)`);
- `ADMIN_ROLE_CODES = {system_admin, security_admin}` — роль `operator` в него **не входит**.

Следствие: пользователь с одной unscoped-ролью `operator` получает `is_admin=false`, пустой
advertiser-scope и, как производную от него, **пустой retailer-scope** → fail-closed → **ноль
строк на всех 36 FORCE-RLS таблицах**. Все admin-смоуки этого не видят, потому что идут под
`break_glass_admin` (`system_admin` → `is_admin=true` → bypass).

**Статус доказательства — честно:** это вывод из двукратного чтения кода плюс мой утренний
DB-прогон, где пустой scope давал 0 строк. Поведенчески под ролью `operator` я это **не**
проверял. Falsifiable-эксперимент дешёвый: завести пользователя с unscoped `operator`, вызвать
`resolve_scope_context`, проверить `retailer_scope_ids` и счётчики. Готов выполнить на
одноразовой БД и приложить результат отдельной записью.

Если подтвердится — C3 повышается с 🟡 (документация) до 🔴 (функциональный разрыв), и пункт 5
CA-2 «прогонять не только под break-glass» становится не пожеланием, а тестом, который сразу
покраснеет.
