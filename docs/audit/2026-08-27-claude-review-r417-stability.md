## 3. Ответ владельцу: что заставит менять ТЗ по ходу проекта

Текст r417 внутренне согласован. Но **Дополнение I показывает 26 из 26 решений открытыми**
— ни одно не помечено принятым. ТЗ, в котором открыты 26 развилок, будет меняться при
каждой из них — это не дефект текста, это его конструкция. Стабильность теперь покупается
не редактурой, а решениями.

Причём два реестра уже расходятся по статусу: **OD-002 (Ed25519/HMAC) и OD-005
(managed-first) утверждены вами**, а их двойники DEC-003 и DEC-011 в Доп. I числятся
открытыми. Это и есть цена второго реестра (A4).

### 3.1 Источники нестабильности, по убыванию

| # | Источник | Что произойдёт без решения | Как заморозить |
|---|---|---|---|
| 1 | 26 открытых DEC | каждая реализация будет «решать» на месте, ТЗ — догонять | лист решений §4; 13 закрыть до APPROVED |
| 2 | 51 REQ без acceptance-пути | требование будет переинтерпретировано при реализации | `SC-*` для каждого до APPROVED (A3) |
| 3 | 5 внешних prerequisite (AQ.1 №5) | домены v2.6 P1–P3 «уточняются» по мере появления данных | держать `blocked` с триггером; ТЗ не меняется, меняется статус |
| 4 | DEC-023 модель ролей | любая UI-работа под 8 персон при 5 ролях породит правки и registry, и ТЗ | решить **первым** |
| 5 | Числа `proposed` (0.1 %, 100 admin, retention) | всплывут при нагрузочном тесте и у юриста | DEC-009, DEC-007 |
| 6 | Расхождения код↔требование (§6) | каждое — задача, не правка ТЗ, **если** DEC-024/025/026 приняты | принять три решения |
| 7 | Операционные детали внутри ТЗ (стенды, стек AJ, агентский процесс) | меняются чаще требований и тянут ревизию всего документа | вынести в приложения с отдельным change control (§34) |

### 3.2 Правила заморозки после APPROVED

1. Ядро ТЗ (требования + реестр решений) и приложения (окружения, стек, процесс) имеют
   **разный change control**: ядро — только через DEC + changelog + traceability; приложения —
   через owner gate соответствующего типа.
2. Расхождение кода с ТЗ разрешается по ADR-020: либо код к требованию, либо новый DEC —
   никогда правкой требования под код.
3. Домены `blocked` не удаляются и не переформулируются — у них меняется только статус по
   триггеру.
4. Один реестр решений — `roadmap.yaml:owner_decisions`; DEC — alias.
5. Машинная traceability под гейтом: требование без задачи или сценария — красный.
