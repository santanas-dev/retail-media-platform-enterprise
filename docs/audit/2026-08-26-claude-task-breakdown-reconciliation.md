## 0. Корректировка моей предыдущей записи

В `2026-08-26-claude-reconciliation.md` §1 я зафиксировал расхождение «технических строк:
Codex 93 / у меня 106» как открытое. **Оно разрешилось в пользу Codex.** Приёмка RM-GOV-002
(«93 technical items, 13 section rows») дала ключ к определению:

```
непустых строк = 106 · из них с модулем 'SECTION' = 13 · items = 93   ✅ совпало
```

Моё определение секционной строки («заполнена одна ячейка») было неверным: у SECTION-строк
заполнены две — модуль и название раздела в поле статуса. Расхождение снимаю.

Второе расхождение (21 / 28 статусов вне словаря) остаётся **определительным**: среди 93 items
по моему словарю их 14. Спорить бессмысленно — предлагаю в финальной редакции зафиксировать
одно определение. Неоспоримое ядро, которое считается одинаково при любом словаре:

- **3 строки, где в колонке «Модуль» записан номер тикета** — `S-086`, `S-087`, `S-088`;
- **8 строк, где поле статуса содержит S-номера/CI/длинный отчёт** вместо значения словаря
  (`Inventory / Reservations`, `Admin User Management`, `AD/LDAPS Settings UI`,

## 3. Десять конкретных поправок

### P1 · Добавить `RM-GOV-006` — снять противоречие порядка истины 🔴

A1 — не мелочь канона, а **правило, которое легитимизировало B1**: `CLAUDE.md` ставит код выше
архитектурных документов, а `docs/00-source-of-truth/README.md` — ТЗ выше кода до нового ADR.
Пока оба правила в силе, расхождение «в коде HMAC, в каноне Ed25519» формально разрешимо в обе
стороны, и следующее такое расхождение узаконится так же.

Задача: одно определение порядка истины, записанное в одном месте; явное правило для случая
«код разошёлся с папкой источника истины» (требуется ADR, иначе это дефект). Зависит от Gate G,
блокирует `RM-STAB-010`.

### P2 · `RM-GOV-001`: добавить поле гранулярности доказательства 🟡

Модель зрелости без него воспроизведёт «74% CI-enforced» с той же завышенной доказанностью:
43 функции покрыты 38 смоуками, пять commerce-функций делят `commerce__order_create`.
Предлагаю поле `proof_granularity: dedicated | shared:<smoke-id>` и запрет `ci_enforced` без него.

### P3 · Развести решения и реализацию 🟡

Пять пунктов из сорока — **решения владельца, а не работа агента**: `RM-STAB-003` (persona),
`RM-STAB-010` (Ed25519/HMAC), `RM-BIZ-001` (self-service scope), `RM-TECH-206` (license boundary),
`RM-ENV-001` (retire/upgrade окружений). При правиле «один implementation task за раз» цифра 40
завышает очередь реализации: фактически её **≈35**.

Предлагаю поле `kind: decision | implementation` и **выносить все решения владельцу заранее**
(§4) — иначе каждое из них останавливает цепочку на round-trip.

### P4 · Устранить пересечение владения guard'ами 🟡

`RM-GOV-004` в приёмке содержит «smoke semantics», `RM-STAB-005` — «AST guard» для смоуков.
Две задачи определяют пересекающиеся проверки. Предлагаю: `RM-GOV-004` владеет структурными
проверками (drift generated files, schema, метрики, единственность SSOT), `RM-STAB-005`
**расширяет** его правилами семантики смоуков, а не заводит второй guard.

### P5 · `RM-STAB-008` меняет `AGENTS.md` — нужен owner gate 🔴

Приёмка требует «AGENTS, workflow и generated roadmap совпадают», то есть правку контракта
репозитория. Это канон. Собственное дополнение Codex `CA-3` прямо говорило: «Изменение
репозиторского контракта требует явного решения владельца». В приёмке `RM-STAB-008` gate
отсутствует. Добавить.

### P6 · `RM-STAB-004` содержит миграцию — protected boundary назвать явно 🟡

`CLAUDE.md` относит миграции к защищённым границам. `RM-STAB-003` даёт «owner approval до кода»,
что покрывает дизайн, но в приёмке `RM-STAB-004` сама миграция как protected boundary не названа.
Добавить строкой, иначе агент вправе счесть, что approval дизайна покрывает и применение.

### P7 · Снять три ложные сериализации 🟢

| Связь | Почему лишняя |
|---|---|
| `RM-STAB-005` → `RM-STAB-002` | разные наборы: `tests/ui-smoke` против `tests/behavioral`; технической зависимости нет |
| `RM-STAB-009` → `RM-STAB-001` | закрепление зависимостей CI не связано с контрактом env-переменной |
| `RM-ENV-001` в pilot-развилке | зависит только от Gate G и стоит часы |

Снятие не ускоряет исполнение (правило «одна задача за раз»), но **расширяет окно готовых
задач**: если одна упирается в решение владельца, очередь не встаёт.

### P8 · `RM-ENV-001` поднять в этап G 🟡

Инвентарь окружений сейчас после Gate U. Но `.77` **мёртв** (проверено: `curl` → `000`), DEV
на схеме `033`, PROD на `028`, стенд на `036`. Пока это не зафиксировано, любой участник может
потратить проверку на устаревший контур в течение всего этапа S и U — а этап S как раз
восстанавливает доверие к доказательствам. Ставить сразу после `RM-GOV-005`.

### P9 · Четыре приёмки не проверяемы как написаны 🟡

| Задача | Проблема | Предлагаю |
|---|---|---|
| `RM-UX-003` | «согласованная route matrix» — матрица не существует | назвать артефакт и завести его в `RM-UX-001` |
| `RM-UX-004` | «единые состояния, локализация… без broad redesign» — не проверяемо | перечислить конкретные состояния и команду проверки |
| `RM-UX-006` | «15 routes audited» — список маршрутов не зафиксирован | приложить список как артефакт задачи |
| `RM-TECH-204` | решение ИБ по HTML5 внутри implementation-задачи | вынести в реестр решений (P3) |

Правило, которое предлагаю применить ко всем: **приёмка называет команду, CI-job или
именованный артефакт** — иначе её нельзя ни выполнить, ни оспорить.

### P10 · Gate S объявляет debt-пометки, но их никто не проставляет 🟡

Формулировка Gate S: «спорные proof помечаются debt, а не молча переписываются». Верно, но
**ни одна задача этого не делает**: `RM-GOV-002` распоряжается строками roadmap, а не статусами
registry. Нужен явный пункт — где и чем помечается спорный proof (поле в registry или
evidence-ref со статусом `disputed`), иначе Gate S не исполним.

## 4. Решения, которые нужно получить заранее

Чтобы цепочка не вставала (P3), предлагаю вынести владельцу **одним пакетом до старта
`RM-GOV-001`**:

1. Порядок истины «код vs папка источника истины» (P1, `RM-GOV-006`).
2. Ed25519 или легализация HMAC отдельным ADR (`RM-STAB-010`).
3. Internal personas: retailer-scope как первоклассное измерение / внутренние роли как admin /
   признать `operator`+`analyst` нерабочими (`RM-STAB-003`).
4. Политика UI-smoke: blocking или non-blocking (`RM-STAB-008`, правка `AGENTS.md`).
5. Состав control-plane pilot: входит ли `self.campaign_create` (`RM-BIZ-001`).
6. License peak/grant boundary (`RM-TECH-206`).
7. Судьба окружений `.77` / DEV / PROD (`RM-ENV-001`).
8. Механизм MFA и согласование NATS с ИТ — в реестр решений, срок не связан с очередью.
