## 2. Три блокирующие поправки

### B-1 · `roadmap.yaml` не создаётся ни одной из 42 задач 🔴

**Доказательство.** В финальном кандидате `roadmap.yaml` упомянут дважды: строка 44 (правило
о содержимом) и строка 57 — `RM-GOV-001`, `kind: design`, результат «Schema/mini-design». По
таксономии §2 `design` производит проект, а не артефакт. `RM-GOV-003` (строка 59,
`kind: implementation`) — генератор, который `roadmap.yaml` **потребляет**.

В черновике эта дыра была закрыта: приёмка `RM-GOV-002` заканчивалась словами
«**создан initial YAML без overclaim**» (черновик, строка 36). В финальном кандидате
(строка 58) эта фраза **удалена**.

**Следствие.** Приёмка `RM-GOV-003` недостижима — у генератора нет входа. `RM-GOV-005`
объявляет каноном единственный sequencing SSOT, которого не существует. Этап G не может
дойти до Gate G.

**Точная замена.** В `RM-GOV-002`, колонка «Проверяемая приёмка», после
`…5 blocked features имеют gap/unblock;` вставить:

> `создан initial docs/product/roadmap.yaml, валидный по schema из G001, без overclaim (никакой delivery_status=done без evidence_refs);`

### B-2 · Решение §1.3 меняет модель ADR-018, но ни одна задача его не правит 🔴

**Доказательство.** `ADR-018` (Status: Accepted) фиксирует: строка 31 — «**Уровень 1 —
Retailer (`retailer_id`). Верхний tenant boundary**»; строка 36 — двухуровневая RLS
`retailer_id` + advertiser scope. Фактическая реализация, проверенная мной прогоном
(`2026-08-26-operator-scope-experiment.md`): `packages/domain/scopes.py:132` обрабатывает
только `scope_type == "advertiser"`, а `retailer_scope_ids` **производен исключительно** от
advertiser-организаций. То есть retailer сегодня — измерение данных, но не источник scope.

Утверждённое решение §1.3 делает retailer scope **первоклассной границей**, то есть источником
scope. Это изменение модели ADR-018.

Упоминания ADR в кандидате: строки 19, 20 (шапка), 61 (`RM-GOV-006`), 79 (`RM-STAB-003` —
«mini-design/ADR» без указания, какой), 85 (`RM-STAB-010` — про §1.2), 154 (ADR-019).
**`ADR-018` не назван ни разу.**

**Следствие.** `RM-STAB-004` реализует модель, расходящуюся с Accepted ADR. По утверждённому
правилу §1.1 расхождение «является дефектом до явного ADR». То есть задача по построению
запланирована так, что её результат сразу становится дефектом.

**Точная замена.** В `RM-STAB-003`, колонка «Проверяемая приёмка», после
`mini-design/ADR: persona→permissions→scope;` вставить:

> `ADR-018 явно дополнен или заменён новым ADR о retailer scope как источнике scope (не только измерении данных), со ссылкой на §1.3 и на прогон 2026-08-26-operator-scope-experiment.md;`

### B-3 · Владение guard'ами определено для одной пары из четырёх 🔴

**Доказательство.** §2, строка 46: «`RM-GOV-004` владеет структурным guard. `RM-STAB-005`
расширяет его smoke-semantics правилами, а не создаёт параллельный guard». При этом ещё три
задачи вводят проверяющие механизмы без указания владельца и точки входа:

| Строка | Задача | Механизм |
|---|---|---|
| 57 | `RM-GOV-001` | `schema validator` |
| 61 | `RM-GOV-006` | `targeted doc guard` |
| 80 | `RM-STAB-006` | `validator` для journey-спецификаций |

**Следствие.** Четыре независимые точки входа в `scripts/ci/` и четыре CI job'а вместо одного
расширяемого guard — ровно та фрагментация, которую поправка P4 сняла для одной пары. Это
file-overlap: `RM-GOV-004`, `RM-GOV-006`, `RM-STAB-005` и `RM-STAB-006` пишут в один каталог
инструментов без разграничения.

**Точная замена.** В §2, сразу после предложения о `RM-GOV-004`/`RM-STAB-005`, добавить:

> `RM-GOV-004 — единственная точка входа guard в CI. RM-GOV-001, RM-GOV-006 и RM-STAB-006 добавляют в него проверяемые правила (schema, doc-consistency, journey-spec) как подмодули, а не отдельные CI job'ы.`

## 3. Что проверено и принято без замечаний

**Protected и external gates — закрыты все:** `RM-GOV-001`/`RM-GOV-005` — owner approval;
`RM-STAB-004` — применение миграции разрешается отдельно; `RM-STAB-008` — owner review
contract patch; `RM-TECH-207B` — отдельный device approval; `RM-TECH-208` —
protected-boundary approval; `RM-PILOT-003` — отдельный owner GO; `RM-OPS-001` — отдельный
production scope и явное «не запускается автоматически после pilot»; `RM-BIZ-002` — новый
owner scope.

**Slicing одним агентом:** каждая задача — связное изменение с одним результатом. Разделение
`RM-TECH-207A/207B` на design и implementation корректно: hardware inputs и device approval
разнесены по разным гейтам.

**Восемь решений владельца §1 не пересматривались** — они входные данные проверки.
