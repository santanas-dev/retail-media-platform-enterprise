Retail Media Platform v2.6

Вторая ветка развития: монетизация и доказательство эффективности

Дополняет TZ_Retail_Media_Platform_v2_5_Final_Hermes — не отменяет и не изменяет ни одного его требования. Составлено по итогам бизнес-оценки портала от 2026-07-11 (см. rmp_business_gap_review). Назначение документа — то же, что и у v2.5: спецификация, пригодная для передачи AI-агенту или команде разработки без дополнительных уточнений по объёму работ.

Статус этой ветки: ни один пункт не требует переписывания домена Campaign/Delivery/PoP из v2.5 — все требования аддитивны к существующей архитектуре (см. §0.3). Единственное исключение — решение о модели тенантности (§1), которое нужно принять один раз, до начала разработки остальных пунктов, потому что задним числом оно становится дорогим.

0. Статус документа и границы применения

0.1 Отношение к v2.5

Документ является дополнением (extension), а не редакцией. Все требования v2.5 остаются в силе без изменений. При противоречии между документами приоритет имеет v2.5, а расхождение должно быть явно разрешено отдельным решением, а не молчаливым выбором одного из двух текстов.

0.2 Источник требований

Требования этого документа получены из целевого функционального анализа портала с точки зрения бизнес-заказчика — не из технического аудита кода. Формулировки ниже описывают, ЧТО должна делать система, а не то, как именно это реализовано в текущей кодовой базе.

0.3 Принцип аддитивности

Каждый домен ниже спроектирован так, чтобы не требовать модификации существующих таблиц Campaign/CampaignFlight/CampaignPlacement/CampaignCreative/DeliveryPlan/DeliveryManifest/PopEventRaw и связанной с ними бизнес-логики, за двумя точечными исключениями, отмеченными явно в §4 и §6 — оба ограничены одной функцией/модулем, а не доменом целиком.

1. Приоритет 0 — архитектурное решение до начала разработки

1.1 Модель тенантности [ПРИОРИТЕТ 0 — решить до старта]

Вся текущая модель данных (иерархия Филиал → Кластер → Магазин → Устройство, RLS-политики) неявно предполагает одну розничную сеть. Ни в v2.5, ни в текущей реализации нет понятия «сеть/ритейлер» как отдельного уровня скоупинга.

Требования

Бизнес-заказчик должен явно зафиксировать решением (ADR): остаётся ли платформа однотенантной постоянно, или допускается будущая синдикация инвентаря нескольких розничных сетей под одной рекламной платформой.

Если решение — «допускается синдикация в будущем»: все новые таблицы, вводимые пунктами §2–§8 этого документа, должны с первого дня включать поле retailer_id/network_id (с одним предустановленным значением для текущей единственной сети), а новые RLS-политики должны проектироваться как двухуровневый скоуп (retailer → advertiser), даже если сейчас retailer всегда один и тот же.

Если решение — «однотенантность постоянна»: явно зафиксировать это в ADR как осознанный выбор, чтобы вопрос не поднимался повторно при каждом новом домене.

Критерий приёмки

☐ Существует ADR с явным решением о модели тенантности, до начала работ по §2–§9.

2. Домены разработки — приоритет 1

Наивысшая деловая отдача: напрямую влияют на то, сколько денег система способна принести.

2.1 Измерение эффективности рекламы (Attribution & Sales Lift) [ПРИОРИТЕТ 1]

Назначение

Обеспечить рекламодателю доказательство влияния показов на продажи, а не только факта показа — это ключевое отличие retail media от обычной цифровой вывески и основание для премиальной цены инвентаря.

Функциональные требования

Система должна принимать агрегированные, магазино-уровневые данные о продажах (не персональные чеки) через адаптер master-системы чеков/цен — переиспользуя интеграционный слой, уже предусмотренный архитектурой для синхронизации цены ESL/price checker.

Для каждой кампании должна вычисляться baseline-модель ожидаемых продаж по затронутым магазинам/SKU на основе исторических данных за сопоставимый период до старта кампании.

Должна поддерживаться модель «тестовая группа / контрольная группа» на уровне магазинов (не покупателей): часть охваченных магазинов получает кампанию, часть используется как контроль для расчёта инкрементальности.

Отчёт эффективности должен показывать: baseline, факт, разницу (lift) и, при наличии контрольной группы, доверительный интервал/статистическую значимость.

Данные должны агрегироваться не ниже уровня (магазин, SKU/категория, день) — минимальная гранулярность, исключающая деанонимизацию отдельных покупателей.

Результат должен версионироваться и не пересчитываться задним числом при изменении методологии расчёта (принцип §22.8 v2.5).

Данные (новые сущности)

Критерий приёмки

☐ На пилотной кампании отчёт показывает baseline/факт/lift минимум для одного магазина с контрольной группой; методология зафиксирована и версионируется.

2.2 Self-service кабинет рекламодателя [ПРИОРИТЕТ 1]

Назначение

Снизить операционную зависимость от внутреннего рекламного менеджера для типовых кампаний — текущий кабинет read-only, что линейно ограничивает масштабирование на новых рекламодателей.

Функциональные требования

Реализовать отдельное клиентское приложение (advertiser-facing web), уже присутствовавшее в целевой архитектуре продукта, но не реализованное.

Рекламодатель с ролью self-service должен иметь возможность в пределах своего RLS-скоупа: увидеть доступный инвентарь и прогноз показов, создать кампанию в статусе draft, загрузить креатив, отправить кампанию на модерацию/согласование.

Публикация кампании остаётся строго через существующий workflow согласования (draft → moderation → review → approved) — self-service не отменяет модерацию контента и бизнес-согласование, только этап создания и подачи заявки.

Должны быть настраиваемые guardrails: бюджетный/объёмный лимит, при превышении которого требуется ручное подтверждение менеджера; автоматическая проверка конфликтов инвентаря на этапе создания, доступная self-service клиенту через тот же расчёт, что видит внутренний менеджер.

Кредитный/бюджетный лимит рекламодателя должен проверяться на этапе создания кампании, не только по факту (биллинг остаётся вне периметра платформы согласно §2.2 v2.5).

Данные (новые сущности)

Критерий приёмки

☐ Рекламодатель проводит кампанию от создания до публикации без действий внутреннего менеджера, кроме финального approve; все self-service действия проходят через тот же RBAC/RLS-контур, что и внутренний UI.

3. Домены разработки — приоритет 2

Снижение операционного риска и подготовка следующего уровня монетизации.

3.1 Конкурентное разведение (Competitive Separation) [ПРИОРИТЕТ 2]

Функциональные требования

Каждый бренд/рекламодатель должен иметь категорию конкурентности (товарная категория/отрасль).

При формировании плейлиста/manifest система должна проверять и предотвращать (либо требовать явного подтверждения при ручном override) размещение конкурирующих категорий подряд в одном временном окне на одной поверхности показа.

Правило разведения должно быть настраиваемым: минимальный интервал между конкурирующими показами, список исключений по категориям.

Ручной override правила должен фиксироваться в аудите с указанием причины.

Данные

Новое поле competitive_category на сущности Brand/AdvertiserOrganization; новая таблица CompetitiveSeparationRule.

Критерий приёмки

☐ Попытка запланировать конкурирующий показ в запрещённом окне блокируется либо требует явного подтверждения с указанием причины.

3.2 Аудиторный (магазино-уровневый) таргетинг [ПРИОРИТЕТ 2]

Функциональные требования

Система должна поддерживать таргетинг кампании по анонимным атрибутам магазина (ценовой сегмент, средний чек, профиль трафика) — без привязки к личности покупателя, в дополнение к уже существующему таргетингу по SKU/зоне/магазину.

Атрибуты магазина должны загружаться через существующий адаптерный слой master-данных, без нового отдельного источника интеграции.

Таргетинг по этим атрибутам встраивается в существующий механизм таргетинга placement как дополнительное измерение, не отдельная подсистема.

Критерий приёмки

☐ Менеджер или self-service рекламодатель может выбрать набор магазинов по аудиторному атрибуту при создании размещения.

3.3 Контракт интеграции с финансовой системой [ПРИОРИТЕТ 2]

Функциональные требования

Система должна экспортировать (API или файловый экспорт) данные, необходимые для выставления счетов во внешней системе: рекламодатель, договор/заказ, период, объём, тариф, статус выполнения.

Экспорт должен быть версионируемым и идемпотентным — повторный запрос за тот же период не создаёт дублей на стороне потребителя.

Система должна принимать обратный статус (оплачено/не оплачено/частично) от внешней системы через тот же контракт, обновляя уже предусмотренное §22.12 v2.5 поле статуса оплаты кампании.

Критерий приёмки

☐ Пройден минимум один сквозной тестовый цикл: экспорт → (симулированный) ответ об оплате → обновление статуса в портале.

4. Домены разработки — приоритет 3

Точки расширения и дифференциаторы следующего этапа роста — не блокируют пилот.

4.1 Точка расширения под программатик-спрос (проектирование, не реализация) [ПРИОРИТЕТ 3]

Функциональные требования

При проектировании Inventory & Planning Service (ещё не реализован согласно §6.3 v2.5) явно предусмотреть API-контур для будущего внешнего спроса (SSP-facing availability API), не завязанный на внутренний UI создания кампаний.

Автоматическая закупка внешними DSP/SSP по-прежнему не реализуется в этой ветке (сохраняется исключение §2.2 v2.5) — только контракт данных и явное место в архитектуре.

Критерий приёмки

☐ ADR фиксирует точку расширения; реализация API откладывается явным решением, а не умалчиванием.

4.2 Динамический креатив (MVP на одном канале) [ПРИОРИТЕТ 3]

Функциональные требования

Для одного пилотного канала (рекомендуется ESL/price checker, уже интегрированный с master-системой цен) реализовать базовый механизм переменных в шаблоне креатива: подстановка актуальной цены/промо-метки на момент генерации manifest.

Динамическая часть контента должна быть явно помечена как таковая отдельным полем manifest — не смешиваться со статическим, content_hash-проверяемым содержимым.

Портал остаётся не источником истины цены — только транслятором уже подтверждённого значения из master-системы (сохраняется принцип §23 v2.5).

Критерий приёмки

☐ На пилотном ESL-шаблоне подстановка цены отражает изменение в master-системе в течение согласованного SLA (например, следующего цикла обновления manifest).

4.3 Мобильное приложение для полевых операций (MVP) [ПРИОРИТЕТ 3]

Функциональные требования

Минимальный мобильный клиент (допустимо mobile web, не обязательно нативное приложение) для сотрудника магазина: список устройств своего магазина со статусом, подтверждение работоспособности экрана с фотофиксацией, форма быстрого инцидента.

Аутентификация через существующий пользовательский RBAC-контур, без отдельной системы логинов.

MVP не включает управление контентом, публикацию кампаний или административные функции — только диагностику и подтверждение на месте.

Критерий приёмки

☐ Сотрудник магазина подтверждает статус устройства и заводит инцидент со своего телефона без обращения в ИТ.

4.4 A/B-тест — бизнес-метрика победителя [ПРИОРИТЕТ 3, зависит от §2.1]

Функциональные требования

После появления домена измерения эффективности (§2.1) существующее требование к A/B-тестированию (§6.2 v2.5) должно быть дополнено: метрика победителя должна поддерживать выбор между delivery-метрикой (показы/PoP) и lift-метрикой (прирост продаж), а не быть ограничена только показами.

Критерий приёмки

☐ Пилотный A/B-тест завершается решением на основе lift-метрики там, где доступны данные обеих групп.

5. Домены разработки — приоритет 4

Дизайн-заглушки: явно задокументировать намерение, не реализовывать сейчас.

5.1 Стороннее измерение/аккредитация DOOH-аудитории [ПРИОРИТЕТ 4 — дизайн]

Функциональные требования

Явно задокументировать (ADR) архитектурную готовность подключения стороннего измерителя как контракта экспорта PoP/manifest-данных в согласованном формате.

Реализация интеграции с конкретным измерителем — вне рамок этой ветки, выполняется по отдельному решению при появлении рекламодателя/партнёра, требующего аккредитации.

Критерий приёмки

☐ ADR существует и явно помечает пункт как «спроектировано, не реализовано» — в отличие от v2.5, где этот пункт не был упомянут вовсе.

6. Приоритизация и фазы

Рекомендуемая последовательность реализации. Приоритет 0 — предварительное условие для всего остального и должен быть закрыт первым, независимо от порядка разработки самих доменов.

7. Общие принципы (наследуются из v2.5)

Все новые сущности следуют тем же принципам версионирования и неизменяемости истории (§22.8 v2.5).

Все новые API проходят через тот же RBAC/RLS-контур без исключений.

Все новые интеграции с внешними системами (финансовая система, измеритель, master-данные) — только через явно определённый, версионируемый контракт данных, не через прямой доступ к БД.

Ни один пункт этой ветки не требует переписывания домена Campaign/Delivery/PoP из v2.5 — только расширения (см. §0.3 и отдельную оценку «рефакторинг vs новая ветка» от 2026-07-11).

Персонализация на уровне конкретного покупателя остаётся вне рамок навсегда, как и в §2.2 v2.5 — весь аудиторный/attribution-функционал в этой ветке проектируется на агрегированном, магазино-уровневом, анонимном контуре.
