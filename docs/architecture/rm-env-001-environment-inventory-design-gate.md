# RM-ENV-001 — mini-design: инвентарь окружений

**Статус:** работа выполнена, `delivery_status: verification` — `owner_gate: scope_decision`
не выдан
**Задача:** `RM-ENV-001` (этап E0, зависит от Gate G)
**Утверждённая приёмка:** versioned environment inventory; `.81/stand-27dc397` baseline;
`.77` только `unreachable at check time`; DEV/PROD `not evidence`; retire/upgrade остаётся
owner decision.

---

## 1. Что инвентаризовано — и чем это проверено

Каждое поле получено прогоном, а не переписано из документов.

| Окружение | Достижимость | Идентичность | Доказательство? |
|---|---|---|---|
| `stand-81` — `192.168.110.81` | HTTP 200 | `stand-27dc397`, git_sha `27dc397`, schema `036`, environment `staging` — из `GET /version` | **да** |
| `preview-77` — `192.168.110.77` | HTTP **000** на `:3000`, `:3001`, `:8000` | не наблюдалась | нет |
| `santa2-dev` — `:3100` | HTTP 200 | отсутствует | нет |
| `santa2-prod` — `:3000` | HTTP 200 | отсутствует | нет |
| `github-actions` | — | SHA даёт сам GitHub | **да**, но только о поведении на SHA |

Стенд сверен с `base.stand_baseline` в `docs/product/roadmap.yaml`: bundle, git_sha и
schema_head совпадают. Сверка выполняется гейтом на каждом прогоне, а не однократно.

## 2. Почему DEV/PROD — не доказательство: три проверенные причины

Приёмка требует объявить их `not evidence`. Объявления мало — вот почему это так:

1. **Общий API.** Оба портала обслуживает **один** control-api на `:8000`. Наблюдение в
   «PROD-портале» не является наблюдением PROD-стека.
2. **API не сообщает идентичность.** `GET /version` отдаёт `version=dev`,
   `git_sha=unknown`, `schema_head=null`. Привязать наблюдение к коммиту нечем.
3. **API работает из изменяемого рабочего клона.** `readlink /proc/<pid>/cwd` →
   `/home/santa2/work/retail-media-platform-enterprise`, процесс запущен
   `2026-08-25 14:26:31`, без `--reload`. Исполняется код дерева на момент старта;
   клон с тех пор ушёл вперёд. Соответствия какому-либо зафиксированному SHA не существует.

Дополнительно: несмотря на имя, PROD-портал поднят Vite dev-сервером
(`vite --host 0.0.0.0 --port 3000`), то есть это не production-сборка. Порталы работают
из отдельных клонов — `contours/dev` @ `1b0452c` (develop), `contours/prod` @ `b5dd3b3` (main) —
но их SHA к наблюдению не привязывается, потому что бизнес-логику отдаёт общий API.

## 3. Формулировка про `.77` — наблюдение, а не решение

По OD-007 допустимо ровно `unreachable at check time`. Слова «мёртв», «выведен из
эксплуатации», `retired`, `decommissioned` запрещены: недостижимость на момент проверки —
наблюдение, а вывод из эксплуатации — решение владельца, которое не принято.

Правило проверяется на **структурном поле** `disposition`, а не сканированием прозы.
Первая моя реализация сканировала текст и немедленно покраснела на собственном пояснении
инвентаря, где эти слова перечислены как запрещённые. Это тот же класс дефекта, который
владелец нашёл в детекторе `SUPERSEDED`, и чинить его надо в корне: правило читает поле,
а свободный текст на вердикт не влияет. Отдельный **зелёный** tamper-кейс охраняет
отсутствие этого ложного срабатывания.

## 5. Модуль `env` гейта

Владелец правила — `RM-ENV-001`; регистрируется в едином entrypoint, своего CI-job не
заводит (B-3).

| Проверка | Что ловит |
|---|---|
| `MISSING` / `EMPTY` / `NO-CHECK-DATE` | инвентаря нет, он пуст или не говорит, когда проверялся |
| `INCOMPLETE` / `DUPLICATE` | окружение без обязательного поля; повтор id |
| `EVIDENCE-WITHOUT-IDENTITY` | окружение объявлено доказательным без закреплённого `git_sha` |
| `EVIDENCE-UNREACHABLE` | доказательным объявлено недостижимое окружение |
| `UNREACHABLE-WITH-IDENTITY` | у недостижимого окружения записана идентичность, которая не наблюдалась |
| `DISPOSITION` | disposition вне допустимого для роли — в частности, `.77` объявлен решением, а не наблюдением |
| `NO-OWNER-DECISION` | не сказано, что retire/upgrade остаётся за владельцем |
| `BASELINE-MISMATCH` | стенд в инвентаре разошёлся с `base.stand_baseline` |

**Живость не проверяется намеренно.** У CI нет маршрута в эту LAN, и проверка живости,
которая молча зеленеет из-за недоступности сети, была бы ложью — ровно тем классом
дефекта, против которого стоит весь этап G.

Шесть tamper-кейсов измерения `env`, из них один зелёный-охранный. Матрица гейта:
25 → **31/31** по девяти измерениям.

## 6. Почему статус `verification`, а не `done`

Задача несёт `owner_gate: scope_decision`, и он не выдан. Приёмка прямо оставляет
решение «retire или upgrade `.77`» владельцу — это и есть содержание гейта.

Проверяется машинно: правило `OWNER-GATE-UNGRANTED`, добавленное вместе с закрытием
Gate G, не позволяет задаче с невыданным owner gate стоять в `done`. Оно же нашло, что
`RM-GOV-001` был закрыт при невыданном гейте — запись о вашем ACCEPT проставлена задним
числом, потому что схема до этого не имела места для факта утверждения.
