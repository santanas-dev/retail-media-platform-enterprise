# RM-STAB-002 — mini-design: strict RLS context по умолчанию

**Статус:** реализовано, `delivery_status: verification` — жду прогона CI
**Задача:** `RM-STAB-002` (этап S, зависит от `RM-STAB-001`)
**Закрывает находку:** `BEHAVIORAL-ADMIN-MASK-001` (мой аудит 2026-08-26)
**Утверждённая приёмка:** admin elevation только setup; endpoint allowlist;
context tamper красный; behavioral subset зелёный.

---

## 1. Дефект

`tests/behavioral/conftest.py` открывал **каждый** запрос с
`app.rmp_is_admin='true'`. Сброс в `false` живёт в `resolve_scope_context`, который
вызывается только через `set_rls_context`. Значит эндпоинт, **забывший** контекст,
в тестах видел все строки, а в проде — ни одной.

Набор структурно не мог поймать класс `INVENTORY-RLS-CONTEXT-001` / `/auth/me`.
Отказывался от маски ровно один файл (`strict_client` в
`test_authz_cross_portal_001_derived_rls`).

## 2. Замер до реализации

Наивное переключение на strict ломает **181 из 470** тестов. Разбивка по фазам
оказалась решающей:

| Фаза | Поломок |
|---|---|
| setup | 148 |
| teardown | 13 |
| тело теста (`call`) | 20 |

То есть маска в основном подпирала **построение состояния**, а не сами проверки.
Отсюда форма решения.

## 3. Решение — элевация привязана к фазе

`pytest_runtest_setup` и `pytest_runtest_teardown` включают элевацию,
`pytest_runtest_call` выключает. Это «admin elevation только setup» буквально:
пока pytest строит и разбирает состояние, запросам разрешён admin-обход; в теле
теста сессия открывается ровно как в проде.

Результат: **0 setup/teardown-поломок**, осталось 30 тел тестов — то есть ровно
те, что держались на маске в момент проверки.

## 4. Что вскрыли эти 30 — продовый дефект, а не тестовый артефакт

Все 30 падали на одном: RLS отвергает работу с `device_onboarding_codes`.

Проверено по цепочке, без предположений:

1. `POST /identity/device-codes` и `POST /device/onboard` **не несут**
   `Depends(set_rls_context)` — при том что 112 из 124 эндпоинтов несут.
2. Продовый `get_db` не ставит ни `app.rmp_is_admin`, ни scope: он только открывает
   транзакцию.
3. Политики `device_onboarding_codes_{sel,ins,upd}` требуют `rmp_is_admin=true`
   либо совпадения `retailer_id` со scope. Таблица — `FORCE RLS`.

**Прямое доказательство из базы:**

| Кто читает активный код | Видит |
|---|---|
| Владелец с контекстом `admin` | 1 |
| Роль приложения **без контекста** — это прод `/device/onboard` | **0** |
| Роль приложения с контекстом `admin` | 1 |

Следствие: в проде каждое устройство получает `403 INVALID_CODE`, а создать код
нельзя вовсе. **Self-onboarding не работает.** Латентно только потому, что пилот
не развёрнут и плеер КСО ещё не в enterprise-репозитории.

Из 12 эндпоинтов без контекста остальные 11 законны: `/login`, `/refresh`,
`/logout`, `/change-password` работают до аутентификации; `/batch` — под
device-auth; `/advertiser-applications` и приём инвайта публичны; `/roles`,
`/permissions`, `/audit-events` читают глобальные не-RLS таблицы.

Это шире моего августовского аудита: тогда я смотрел `identity_routes` и написал
«111/114, три исключения безобидны». `device_routes` в тот срез не входил.

## 5. Allowlist — подотчётный, а не удобный

`ENDPOINT_ELEVATION_ALLOWLIST` содержит две записи. Каждая несёт идентификатор
дефекта, доказательство и фразу «снимается починкой эндпоинта, а не правкой теста».
Подотчётность проверяется тестом: запись без идентификатора `RLS-CONTEXT-`, без
слова «починка» или короче 120 символов — красный. Больше пяти записей — тоже
красный: список не должен подменить собой отключение strict-режима.

`skip` и `xfail` не использованы: контракт их прямо запрещает, и смысл был бы
обратным — они спрятали бы ровно то, что задача вскрывает.

## 6. Решение владельца по объёму

Владелец 2026-08-26: закрыть `RM-STAB-002` в объёме harness, починку device-маршрутов
вынести отдельной задачей. Заведена **`RM-TECH-210`** (этап BT, `owner_gate:
device_contract`), её приёмка требует снятия обеих записей allowlist при зелёном наборе.

Задача несёт owner gate не формально: онбординг **неаутентифицирован**, поэтому scope
нельзя вывести из пользователя. Нужен либо явный контекст под предъявленный код, либо
отдельная политика — это решение о модели безопасности, а не правка кода.

## 8. Две ошибки процесса, допущенные и исправленные

Первый замер оборвался: я сделал `git stash` по `conftest.py`, пока по нему шёл
pytest. Второй был невалиден — БД осталась загрязнённой от предыдущего прогона, и
внешние ключи блокировали очистку, давая 293 каскадные ошибки. Оба результата
выброшены; стенд теперь пересоздаётся скриптом перед каждым замером.
